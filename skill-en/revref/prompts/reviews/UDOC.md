# UDOC — User documentation

Finding ID prefix: UDOC. Use together with `prompts/common-rules.md`.

Review the user documentation: help, user manual, installation and setup instructions, FAQ, knowledge base. Do not assess the code or the technical documentation for developers — check against them only the actual behavior of the product.

Audience. Determine who the documentation is written for (beginner, experienced user, administrator), whether the level of presentation matches that audience, and whether levels are mixed on one page.

Completeness. Build a coverage matrix: each user-visible function, screen, setting and error message → where it is described → status: described / partially / not described / described but no longer in the product. Pay special attention to: a quick start up to the first successful result, typical scenarios, error messages with an explanation of what to do, a troubleshooting section.

Freshness and accuracy. Do the names of buttons, menu items, fields and default values match the current interface? Are there outdated screenshots, descriptions of removed features, historical notes in the style of "it used to be like this, now it is like that"? Is it stated which product version the documentation applies to?

Clarity. Is the terminology consistent (one concept — one term, matching the labels in the interface)? Is a glossary needed? Is there incomprehensible jargon or implementation detail the user does not need? Are instructions step by step: one step — one action, prerequisites stated before the steps, the expected result after key steps?

Sufficiency and excess. Where is information lacking to complete a task without outside assistance? Where is there excess: filler, the same thing repeated on different pages (with a risk of the copies diverging), obvious things, overload of detail? What should be merged, shortened or deleted?

Structure and navigation. Are the material types separated: step-by-step instructions, reference, explanation of concepts, troubleshooting? Are the table of contents and section order logical? Can the answer to a typical question be found within 30 seconds? Are there cross-references, and no broken links or dead-end pages?

Tables. Are they used where they actually help (comparisons, parameters, mappings) rather than for running text? Are headers clear, are units of measurement given, are there overloaded tables that would be better split? Are they readable on a narrow screen?

Illustrations. Are there screenshots and diagrams where text has a hard time explaining, and no superfluous ones where one sentence is enough? Are screenshots up to date, are the relevant elements highlighted on them (arrows, frames, step numbering), is the resolution sufficient, has no personal or test data ended up in the frame? Is the style consistent, are there captions and alt text?

User test. Pick 3–5 typical user tasks and go through them strictly by the documentation, as a beginner would. Describe where you got stuck, what you had to guess, and where the instructions diverge from actual behavior.

Response format, in addition to the common rules: the coverage matrix; findings by the blocks above; a list of pages to merge and delete; a list of missing pages with a brief content outline for each. If there is no user documentation, propose a minimally sufficient structure.
