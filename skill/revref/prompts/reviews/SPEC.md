# SPEC — Соответствие ТЗ и технической документации

Префикс ID находок: SPEC. Применяй вместе с `prompts/common-rules.md`.

Проведи ревью соответствия реализации техническому заданию (ТЗ) и технической документации: README, документации по архитектуре и API, описанию конфигурации, changelog. Действуй как ИТ-аудитор и системный аналитик. Пользовательскую документацию (справку, руководство) не оценивай — для неё есть отдельное ревью.

В проекте могут быть и несоответствия кода ТЗ, и отставание ТЗ от реализованного функционала. Если ТЗ нет, используй в качестве эталона README и прочие описания проекта.

1. Матрица трассируемости: каждое требование → где реализовано (файл, модуль) → статус: реализовано / частично / не реализовано / противоречит / реализовано сверх ТЗ (функционал есть в коде, но не описан).
2. Расхождения: в каждом случае разберись, что правильнее исправить — код или документацию, и обоснуй. Если однозначно решить нельзя, вынеси вопрос в «Вопросы владельцу» с рекомендацией.
3. Качество документации: записи, не соответствующие логике; исторические записи в стиле «раньше было так, а теперь так»; запутанные, противоречащие друг другу или сами себе факты; одни и те же сведения, продублированные в разных документах.
4. Работоспособность инструкций: шаги установки и запуска из README действительно работают (выполни их, если возможно); все переменные окружения, параметры конфигурации, эндпоинты API и команды описаны и соответствуют коду.

Предложи правки списком по документам и разделам: изменить / удалить / добавить (с текстом). Для удаляемых блоков документации укажи, не теряется ли нужная информация.
